============================================================
1. PROJECT OVERVIEW
============================================================

Project title:
Multi-Agent Warehouse Robot Coordinator

Short explanation:
Our project is a simulation-based multi-agent AI system that models a warehouse as a 25x25 grid containing obstacles, packages, and five autonomous robot agents. A coordinator automatically assigns packages to available robots. Each robot uses A* search to find a path, avoids obstacles and other robots, picks up packages, and delivers them. If a robot fails, the package is recovered and reassigned to another active robot. The system is implemented in Python using Pygame.

Current project configuration:
- Warehouse grid: 25 x 25
- Robots: 5
- Packages: 10
- Maximum supported robot failures: 3
- Programming language: Python 3.10
- Visualization/simulation: Pygame 2.6.1
- Pathfinding: A* Search
- Heuristic: Manhattan Distance
- Development environment: VS Code + Conda
- OS used for the project: Windows 11

IMPORTANT:
Ignore older documentation values such as 15x20, 3 robots, 6 packages, or 2 failures. The latest project version uses 25x25, 5 robots, 10 packages, and 3 failures.

10. MAIN ALGORITHM - A*
============================================================

The project uses A* Search for robot pathfinding.

A* is a pathfinding and graph-search algorithm that finds a low-cost path from a starting position to a goal by combining:
- Actual cost already travelled
- Estimated remaining cost

Formula:

f(n) = g(n) + h(n)

Where:

g(n) = actual cost from start to current node

h(n) = estimated cost from current node to goal

f(n) = total estimated cost


============================================================
11. MANHATTAN DISTANCE
============================================================

The project uses Manhattan Distance as the A* heuristic.

Formula:

h(n) = |x1 - x2| + |y1 - y2|

Example:

Current position = (2,3)
Goal = (7,8)

h = |7-2| + |8-3|
  = 5 + 5
  = 10

Why Manhattan Distance?

Because the robots move only in four directions:
- Up
- Down
- Left
- Right

They do not use diagonal movement.

Good viva answer:

"Because our robots move only in four directions on a grid, Manhattan distance is an appropriate heuristic."


============================================================
12. HOW A* WORKS IN THIS PROJECT
============================================================

Basic process:

1. Start from the robot's current cell.
2. Examine valid neighbouring cells.
3. Calculate g(n).
4. Calculate h(n).
5. Calculate f(n) = g(n) + h(n).
6. Select a promising node.
7. Continue searching.
8. Stop when the goal is reached.
9. Reconstruct the path.
10. Robot follows the path.

Obstacle cells are excluded from normal movement.

The implementation uses a priority queue and stores parent information so that the final path can be reconstructed.


============================================================
13. WHY A* INSTEAD OF BFS?
============================================================

Good answer:

"BFS can find a shortest path in an unweighted grid, but it does not use an estimate of how close a node is to the goal. A* combines actual path cost with a heuristic, so it can guide the search toward the destination and is more suitable for our navigation problem."


============================================================
14. WHY A* INSTEAD OF DIJKSTRA?
============================================================

Good answer:

"Dijkstra's algorithm considers accumulated path cost but does not use a heuristic to guide the search toward the goal. A* adds the heuristic component, making the search more goal-directed."


============================================================
15. TASK ALLOCATION
============================================================

Task allocation answers:

"Which robot should perform this package delivery?"

The Coordinator:
1. Finds idle robots.
2. Excludes failed robots.
3. Identifies dropped/recovery packages.
4. Identifies normal waiting packages.
5. Prioritizes dropped packages.
6. Selects the closest available robot.
7. Assigns the package.

The distance used for selection is Manhattan distance.

Example:

Robot 1 = distance 12
Robot 2 = distance 5
Robot 3 = distance 9

Robot 2 is selected because it is closest.


IMPORTANT:
Task allocation is NOT A*.

Task allocation:
- Decides WHO gets the task.
- Uses distance-based greedy selection.

A*:
- Decides HOW the robot reaches the target.
- Performs pathfinding.

18. COLLISION AVOIDANCE
============================================================

There are two kinds of obstacles:

1. Static obstacles:
   Warehouse shelves / blocked cells

2. Dynamic obstacles:
   Other active robots

Before moving, a robot checks its next cell.

If another robot is already occupying that cell:
- The robot does not enter the cell.
- The occupied position is treated as a temporary blockage.
- A* can recalculate an alternate route.


============================================================
19. DYNAMIC REPLANNING
============================================================

Dynamic replanning means recalculating a robot's path when the current planned path becomes unsuitable because the environment has changed.

Example:

Old path:

Robot -> A -> B -> C -> Goal

Another robot occupies C.

The robot:
1. Detects that the next cell is occupied.
2. Treats the occupied position as temporarily blocked.
3. Runs A* again.
4. Finds another valid route.
5. Continues toward the goal.

Important:
Dynamic replanning is implemented in the robot navigation logic. During a live simulation, it was observed when a robot encountered a dynamically occupied path and recalculated its route using A*. Keep the testing documentation consistent with this observation: record the collision-triggered replanning test as passed only if the behavior was reproduced and verified during testing.

============================================================
24. FAILURE RECOVERY
============================================================

Failure recovery is one of the major features.

There are two important cases.


CASE 1: ROBOT FAILS BEFORE PICKUP

Robot is travelling toward package.

Robot fails.

Then:
- Robot becomes FAILED.
- Robot becomes inactive.
- Package returns to its original pickup location.
- Package becomes Waiting.
- Coordinator can assign it to another active robot.


CASE 2: ROBOT FAILS AFTER PICKUP

Robot is carrying a package.

Robot fails.

Then:
- Robot becomes FAILED.
- Robot becomes inactive.
- Package becomes Dropped.
- Package is placed at the recovery/drop location.
- Coordinator identifies the recoverable package.
- Another active robot is assigned.
- Replacement robot travels to the package.
- It picks up the package.
- It continues to the delivery location.

39. ADVANCED VIVA QUESTIONS
============================================================

Q41. Why not let every robot choose its own package?

A:
That would require distributed task negotiation and conflict resolution. Our project uses centralized coordination to make task allocation simpler and consistent.


Q42. What if no valid path exists?

A:
A* returns no valid path. The robot does not proceed along an invalid route, and the task can be released or handled through the available recovery/reassignment logic depending on its state.


Q43. Can two robots be assigned the same package?

A:
The coordinator considers only packages without an assigned robot and removes the selected robot from the current idle set after assignment, preventing duplicate assignment under normal operation.


Q44. What is the difference between a static and dynamic obstacle?

A:
A static obstacle is permanently part of the warehouse, such as a shelf. A dynamic obstacle can change position, such as another moving robot.


Q45. What is centralized coordination?

A:
A central Coordinator makes task allocation decisions for the robot agents.


Q46. What is decentralized execution?

A:
After receiving a task, each robot independently calculates and follows its path and manages its movement.


Q47. Is the system scalable?

A:
The modular structure supports extension, but the current implementation uses a fixed 25x25 environment, five robots, ten packages and a three-failure limit. Larger deployments would require further scalability and scheduling improvements.
